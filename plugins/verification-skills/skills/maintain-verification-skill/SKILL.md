# Maintain a verification skill

A feature map rots the moment the project changes. This skill is the upkeep loop for a skill generated by `create-verification-skill` (or any verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one, and say which:

- **clean**: every feature got source and live coverage; nothing worth changing.
- **changed**: proven doc, harness, or map corrections were written to the skill.
- **blocked**: coverage could not finish or a proven fix could not be applied safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, features/, and any harness scripts it owns). Never edit product code during a run: a behavior the map describes that the project no longer does is either doc drift (fix the map) or a product regression (report it; never rewrite the map's expected result to match it). It is drift only when the change is intentional on the project's own record: its docs, changelog, tests or the commit that made it. Behavior that contradicts the project's own docs or tests is a regression, and an undecidable case is reported as a product gap for the user to call.

## Pass

0. **Locate the target.** Find the skill and confirm its binding as [binding.md](../create-verification-skill/references/binding.md) says, then hold its lock from here until the pass record is written. None → stop and point at `create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Lightweight; no generated inventory.

2. **Source wave.** One read-only reader per feature file: concurrent subagents where the runtime has them, or read them in turn yourself. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. Readers never drive the project and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces (routes, commands, models, metrics) missing from the map, and require a concrete source path before calling one missing. Re-read the pipeline definitions the skill's Pipeline section cites (CI, deploy, scheduled jobs): a step, flag or ordering the section doesn't replay or list as a gap is drift.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, a fresh isolated session per drive for short-lived CLIs, one development build per pass for a dbt project (the skill's Launch section decides, not this one). Exercise every feature and every replayable pipeline shape at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising: doctor before first drive, doctor at the start of each session as the skill's Launch section defines one, doctor again after any drive whose outcome the recipe did not predict (an expected non-zero exit is not one), and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness: failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once (restart whatever the fix invalidated, nothing more) before calling the pass `blocked`. A feature that can't be reached is `unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted, and it is never reported as passed; if the map omits that prerequisite, that's drift. Any corrected recipe or harness fix from triage gets re-driven live before it is kept. Final teardown happens after the last drive of the run, including those re-proofs, so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). Behavior that's actually broken → product gap; record it for the user, and leave the map's expectation as it was. An isolation finding is judged against the threat model in `create-verification-skill` (Interview, Isolate): accidental contact through ordinary use gets fixed, including contact caused by a value the operator inherited without meaning to (a production URL in their shell or a `.env` file). Only something that needs a hostile local process or a deliberately poisoned environment goes to `Known limits`.

6. **Record.** Corrections are written in place under edit scope during the pass; for changed, re-read every changed file before reporting. A promoted skill is the exception: its corrections go to the project repo as one pull request, following that repo's conventions and the publishing rule, merged as [binding.md](../create-verification-skill/references/binding.md) says under "Merging a skill pull request". For every outcome, write `<evidence root>/maintenance-<UTC YYYYMMDDTHHMMSSZ>-<short revision>-<random suffix>.md` beside the run directories (revision driven, runs, features covered, unreachable prerequisites, mocks, gaps, confirmed drift, product gaps, outcome) and report it with the coverage stated honestly.

## Promote to the repo

Only on the user's explicit request ([binding.md](../create-verification-skill/references/binding.md)). Never promote on your own.

1. **Confirm the binding** and hold the lock, as in step 0.
2. **Copy** the skill, without its evidence or lock, into a new branch of the repo at the promoted layout [binding.md](../create-verification-skill/references/binding.md) describes.
3. **Scrub and re-prove.** Apply the publishing rule to every copied file. Rewrite the `Project` section to the promoted binding, and point every evidence writer and lock user, helpers included, at the private directory; Launch creates that directory when missing, so a fresh host's first run works. Then run the copy once from the branch (launch, doctor, one feature, cleanup) and confirm nothing landed in the checkout.
4. **Open one pull request** in the project repo, following its own branch, commit and PR conventions, carrying the latest evidence record's summary under the publishing rule. It merges as [binding.md](../create-verification-skill/references/binding.md) says under "Merging a skill pull request".
5. **Retire the private copy** once that pull request has merged, to the pointer [binding.md](../create-verification-skill/references/binding.md) describes, releasing the lock last.
